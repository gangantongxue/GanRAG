# AI 服务架构选型

## AI 框架

**选型：Eino**

Eino 是字节跳动的 AI 应用开发框架，用于构建基于大语言模型的应用，特点包括：
- 组件化：提供模型调用、RAG、工具调用等标准组件
- 编排能力：支持复杂的 AI 工作流编排
- 可扩展：支持自定义组件和插件
- 与豆包大模型深度集成

## 职责

- RAG 检索增强生成
- AI 模型调用
- 向量检索
- 对话管理
- 多智能体路由与切换（P1.5，见下节）

## 多智能体架构（P1.5）

> **落地状态：设计定稿，代码未实现**（P1.5）——实现后更新 docs/architecture.md「设计落地状态」。

用户每条消息经 **Laya** 决策模型路由到最合适的智能体执行；同一会话内默认沿用当前智能体，满足切换条件才切换。

### 路由选型：Laya

**选型：Laya**（开源 Jev 兼容的 System 1 决策模型，Apache-2.0）

- 非自回归决策模型：一次前向传播回答结构化问题（`choice` 单选 / `score` 评分 / `noul` 是否），不生成文本，33ms 级延迟
- 每个选项输出概率 + 校准置信度 `confidence`（choice 题 = 1−归一化熵），天然支持「符合度排名 + 阈值」策略
- 本地 CPU 可跑（preload 后路由近乎免费），Go 服务经 HTTP 调用

**使用红线**（选型时查证所得）：

- 置信度一律用 `confidence`，**禁用 `act_probability`**（上游 issue #185 证实无信号）
- 模型出厂**过自信**，阈值须用自有数据校准温度后再定，初期保守
- 中文输入走 `laya-multilingual` checkpoint（Laya Router 按语言自动选择）
- 输入只喂「上一条用户消息 + 本条消息」（multilingual 上限 1024 token），**绝不塞全量对话历史**
- 智能体选项超过约 20 个时用 `predict_tournament` 或两级路由（先族后成员）；选项描述（criteria）共享约 256 token 预算，须短而具体

**部署拟议**（P1.5 实现时可调整，不影响本设计）：`laya-serve` sidecar 容器 + HTTP `/v1/systemone`，AI 服务作客户端；备选 ONNX 直跑。

### 智能体注册表

- 配置化定义：智能体 `id`、能力描述（Laya choice 题的 criteria）、system prompt 差异块
- 所有智能体**共用同一底层 LLM 与同一工具集**（含 `search_context`），差异只在 system prompt 的智能体块

### 路由与切换流程（每轮一次 Laya 调用）

1. **首轮**：无当前智能体，Laya `agent` choice 题选智能体；置信度不足时落**默认通用智能体**，不阻塞用户
2. **后续轮**：同一 choice 题，**选项包含当前智能体**；「是否切换」不问模型，由代码粘性策略判定（避免双问答案矛盾，且总结开销后置）
3. Laya 输入 = 上一条用户消息 + 本条消息

**粘性策略**（切换 ⟺ 三条同时满足）：

- `top ≠ 当前智能体`
- `top.confidence ≥ 0.8`（初始值，配置项，P1.5 用真实数据校准）
- `p_current < 0.8 × p_top`（当前智能体概率明显落后）

附带约束：切换后 **2 轮冷却**，禁止连续自动切换；条件不满足时**一律保持现状**——拿不准不动，失败方向偏向稳定。与「排名前 X% 且符合度不低于阈值就不切换」的原始想法等价，但反转了模糊输入的失败方向：全模糊输入下所有选项概率都低，原规则会误切，本规则要求切换有正向证据。

### 上下文压缩（会话级，存 chat_sessions）

**机制**：压缩上下文**不进消息表**，单独存 `chat_sessions.context`，并以 `chat_sessions.context_msg_id` 记录游标——上下文之后需要拼接的起始消息。

1. **拼装**：prompt = 共享基础提示 + 智能体差异块 + `context` + `chat_messages` 中 `id >= context_msg_id` 的消息（按序）；`context` 为空则拼全量历史
2. **压缩 / 切换**：LLM 读「旧 context（若有）+ 游标前的原始消息」生成新 context，**直接替换** `context` 并把 `context_msg_id` 推进到新边界；智能体切换 = 压缩 + 换智能体（新智能体 prompt = 共享提示 + 新智能体块 + 新 context + 当前问题）
3. **原文不删**：被压缩区域的消息保留在 `chat_messages`，供 `search_context` 检索

**好处**：消息表保持纯对话（role 仅 1/2），模型上下文**结构性不进用户页面**；多次压缩一个槽位直接替换，无摘要堆积。

### `search_context(keywords)` 上下文搜索工具（全部智能体共享）

**解决的问题**：上下文压缩后，细节（具体数字、原文引用、早期结论依据、用户早先的约定等）不在 prompt 里；当后续回答**需要这些详细上下文**时，AI 用本工具从完整对话记录中找回。

- **调用时机**：回答需要压缩前对话的具体细节时（引用原文、核对早期数据、确认用户早先约定），由 AI 自主判断调用
- **输入**：关键词（可多个）
- **行为**：在**本会话完整对话记录**中匹配（`chat_messages` 全量原文，**含被压缩区域**），返回命中消息的原文片段及所在位置
- **实现**：复用 `idx_chat_messages_session` 做会话内检索，无新增表；会话内消息量小，LIKE 关键词匹配足够，不建向量索引（YAGNI）
- **效果**：压缩后 prompt 短而省缓存，细节按需召回——上下文「**压缩存储、原文可溯**」

### 缓存命中策略

- Laya 是独立小模型，路由本身**不影响** LLM 的 prompt/KV 缓存；缓存全看执行智能体的 prompt 前缀
- **主杠杆：少切换**——prompt 缓存按前缀匹配，每次切换智能体 = 该会话前缀缓存全部作废
- 前缀排布：**共享基础提示置前缀最前 → 智能体差异块紧随其后**，切换时公共前缀仍命中
- 切换后新 prompt 很短（context + 问题），重建缓存成本有界，后续轮次增量命中

### 配置项（AI 服务配置持有，P1.5 调参）

| 配置 | 初始值 | 说明 |
|------|--------|------|
| `switch_confidence_min` | 0.8 | top 置信度门槛 |
| `switch_margin_ratio` | 0.8 | 当前智能体概率需低于 top 概率的比例 |
| `switch_cooldown_turns` | 2 | 切换后冷却轮数 |
| `default_agent` | 通用智能体 | 低置信度时回落 |

## 向量化与检索路由（P1.5）

> **落地状态：设计定稿，代码未实现**（P1.5）——实现后更新 docs/architecture.md「设计落地状态」。

AI 服务持有**当前向量化模型**配置（稳定 id + 版本，如 `bge-m3`），职责：

- **写入**：文章保存/删除的增量同步后，对 `articles.content` 分块、用当前模型向量化，写入 `kb-<kb_id>-<model_id>` 集合（每条向量 metadata 记 `embedding_model`）
- **检索路由**：查询向量用当前模型编码，**只查当前模型后缀的集合**——用什么模型，就检索对应的向量化结果，切换模型不影响旧向量的可用性
- **切换模型**：新写入切新模型集合 → 按 content 全量重建（不重跑 markitdown）→ 重建完成前旧集合继续服务 → 原子切换配置、下线旧集合（保留期可回滚）
